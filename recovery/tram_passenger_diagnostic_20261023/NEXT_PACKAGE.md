Minimal diagnostic sequence:

1. Confirm the actual single car begins at the retained CENTRAL pose; gates are
   closed, bridges stowed, original cart outside/unlocked/no joint. Record instance
   identities, script paths and retained floor support. Assert no held interaction.
2. Request one real station through the original motor API. Confirm cursor,
   physical-body pose and speed genuinely advance with no fault. Attempt the
   player's single supported in-car spawn at the prescribed moving route point.
   Reuse the current ship arrival's residency/floor/standing-capsule checks where
   the full runtime owner is present; in this isolated fixture repeat its exact
   physics criteria, label it diagnostic, and do not claim full startup arrival.
3. Thereafter make no actor position, velocity, parenting or transform writes.
   Let the original move_and_slide and actual AnimatableBody carry the player.
   Check supported floor, expected platform ownership, cabin-local drift, camera
   identity and continuous car motion through the tight central curve, braking,
   a station stop and reversal. Starting a real empty car is not passenger proof.
4. If that short discriminating leg passes, extend to all five stops and back
   continuously with the same actual actor and car. No resets between legs.
   Check original secured-departure refusal with a deployed/open bridge at a
   separate stationary step; do not bypass the safety adapter.
5. Check original cart/bottle identities and state remained unchanged. Report
   actual failures as failures. A fall, cabin drift, unsupported floor, unexpected
   contact, motion fault or source-pin mismatch ends the diagnostic.

Candidate tolerances must be justified against the real cabin collision and
existing standing/actor_aboard envelope, not selected to hide drift. Keep ordinary
walking, boarding, cart-loaded transit and species/engineering acceptance separate.
Fixed-step headless execution can establish these bounded physics observations,
not GPU performance, normal streaming visibility or whole-ship playability.

## C. Later opt-in performance run, after A and B

- Use the ordinary bootstrap/launcher/readiness/streaming and the real Player
  camera. Add a separate opt-in entry hook; no permanent default spawn change.
- Start actual empty-tram movement via its existing motor request; perform one
  checked spawn into the already-moving cabin. Never continuously position the
  actor or replace the camera route. If the checked spawn fails, abort.
- Automate only existing destination requests. CENTRAL → AFT_MIDSHIP → AFT →
  AFT_MIDSHIP → CENTRAL → FORE_MIDSHIP → FORWARD → FORE_MIDSHIP → CENTRAL is a
  reproducible 1,871.406187 m out-and-back cycle, not an existing autonomous service
  or invented circular route. Preserve every existing speed and safety limit.
- Separate startup/positioning from measured cycle 1 (process-first exposure),
  then repeated warm cycles at the same route phases. Do not claim an OS-cold
  cache without evidence. Three warm cycles are an initial measurement set, not
  automatic proof of a memory plateau; extend only if safely needed to resolve
  the observed trend. Stops/dwell and route phase must match baseline/candidate.
- Fix and record initial original-camera heading/pitch/FOV and whether heading is
  world-relative or car-relative; the original carry diagnostic determines what
  can be held without replacing movement. Do not infer all-direction coverage
  from one heading. Separate additional direction sweeps from walking tests.
- Record engine/source/import/artifact pins, hardware/driver, actual renderer,
  root/world/post viewport sizes, effects, VSync/cap, physics rate, every relevant
  production feature flag, random seed where used, route/dwell/camera definition
  and prewarm baseline/candidate setting. Use the same conditions in both runs.
- Measure real wall frame times separately from process/physics CPU monitors and
  available viewport CPU/GPU render timers. Include mean, p95, p99, worst and
  fraction above16.67 ms. Unavailable GPU timings are unavailable, never zero-cost
  proof. Log bounded intervals and route boundaries, not per-node/per-frame census.
- At those boundaries record node/object/resource counts, engine static/peak and
  render memory, external process RSS/private memory, system/cgroup available
  memory, and existing manager load/release/resident counters. Do not interpret
  detached cached rooms as reclaimed resources. Compare phase-matched late-lap
  baselines/peaks to establish bounded reclamation or continuing growth.
- Start an independent process/system memory watchdog before startup, not after
  a long frame has already consumed RAM. Fresh available-memory preflight is
  mandatory. Abort safely before pressure/crash; retain partial log and reason.
  Current cloud capacity is below the earlier full-run private-memory peak, so a
  whole-ship attempt is not presently justified merely by bounded fixture success.
