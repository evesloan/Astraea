# Astraea architectural delivery rules

Owner direction reaffirmed 6 October 2026: every section on every deck must be represented, including the subsidiary guest, VIP, engineering and true service spaces in the reference blueprints. The entire game takes place aboard this coherent, grand eighteen-deck liner. A programme heading, component asset or floor polygon is not a finished space.

## Shared authority and architectural language
- Use the authoritative master v0.3, current documented overrides, canonical 18-deck datums and exact existing allocation/identity records. Keep conflicting image labels/counts explicitly unresolved rather than silently adopting or discarding them
- Inspect the actual relevant reference images at full size before authoring. Record which spatial features the design implements and which illustrative details cannot fit the approved section
- Resolve plan and vertical section together: footprint, clear heights, multi-level void, capacity basis, views/privacy, arrivals, guest/service circulation, accessible level changes, maintenance and neighbouring volumes
- Author purposeful curves/facets, deep thresholds and reveals, varied connected volumes, inhabited edges and plausible built-in structure. Do not substitute a generic rectangular shell plus decorative strips for the reference architecture
- Reuse the approved editable Blender component families and material palette. Modularity is a construction method, not permission for carbon-copy destinations. Preserve district character and stable room identities
- Guest areas use legible, welcoming architecture and warm source-backed lighting; SunCorp service areas remain more utilitarian. Preserve the existing restrained CRT/low-poly rendering direction
- Keep the complete ship platform ahead of optional furnishing polish. Include furniture/proxies only where needed to establish purpose, capacity, clearance or essential use

## Every package must account for
1. Canonical parent programme keys and all explicitly required child spaces/systems
2. Source evidence, exact dimensional section and conflicts resolved or still open
3. Guest, staff, deliveries, cleaning-cart and emergency interfaces where specified
4. Explicit ownership of compiler floors, asset surfaces, dynamic cabins, doors and protected voids
5. No intrusion into retained homes, neighbours or working routes; no duplicate walkable slabs
6. Real modelled fixture locations, environmental boundaries and truthful source/export/route evidence
7. Unfinished function, furnishing, species fit and final visual acceptance stated plainly

## Coordination and safety
- Each worker owns a distinct named package and explicit file allowlist. Do not edit another package, shared material library, catalogue registry, runtime controller or master layout without coordination
- Reserve any new catalogue identity with the parent before registration. Existing source derivatives preserve their parent identities and unaffected objects; they are not new artistic-design counts
- Preserve original sources and current changes. Parent verifies independent retention before substantial adoption, owns commits and the single backup publisher
- Keep Godot as the engine. No credential/permission changes, purchases, competing backups or workspace restores as part of a package
- Source scripts and pure geometry planning may proceed independently. Parent schedules engine/import/render jobs to avoid competing processes and owns live integration
- Prefer bounded Sol 6.1 assignments, within available concurrency and the owner's ceiling of ten helpers. Start with controllable packages, review their results, and scale only when coordination and usage remain healthy

## Acceptance sequence
Reviewed source/spec section -> editable source and bounded derivatives -> source/export and preservation checks -> independent retention -> live integration -> actual capsule and loaded-cart/control checks -> normal-height in-game/reference review -> matching regression and recorded checkpoint.

No stage implies the next stage passed. Source renders are labelled source-only. Do not claim completed rooms, operating engineering, water simulation, NPC use, target-GPU performance or continuous execution without matching evidence.
